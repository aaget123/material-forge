# 调研与设计 · 素材库架构（综合打包 与 文件统一展示）

针对用户第 6、8 条反馈：

> 6. 添加的综合素材不会放到一起，它会分开放，我要放到一起的那种。
> 8. 文件模式里列表重复（…）；我在选择画廊的时候，我的某一项目文件怎么展示，我觉得应该优化素材库架构，应该可以同时展示图片、视频、声音、音乐、综合、代码、文本和文件。**先上网搜索资源，然后把资料和想法告诉我，我判断是否和我想的一样。**

所以这份文档只做两件事：**列证据**、**给方案**。方案不落地，等用户判断。

## 一、调研：别人怎么处理"一堆文件算一个东西"

| 概念 | 谁在用 | 关键做法 | 来源 |
| --- | --- | --- | --- |
| **堆叠 / Stack** | Adobe Lightroom Classic | 把多张相关照片**堆成一叠**，在图库里只显示一张代表图 + 张数，展开才看到里面的每一张；堆叠里的照片仍然是独立照片（可以单独打分/修改） | [Adobe：Group photos into stacks](https://helpx.adobe.com/lightroom-classic/help/grouping-photos-stacks.html) ✅官方文档标题与功能描述 |
| **集合 / Collection（像播放列表）** | Zotero | 集合是**虚拟的、分层的**；**同一条目可以同时属于多个集合**，加进集合**不会复制**条目；删集合**不会删条目**；父集合默认**不显示**子集合的内容，可以用开关切换 | [Zotero：Collections and Tags](https://www.zotero.org/support/collections_and_tags) ✅已读原文 |
| **复合对象 / Compound object** | 图书馆与数字馆藏领域（JSTOR / OCLC 的元数据规范） | 一个"知识单元"由多个文件组成（例如一本书 = 多页扫描 + 封面 + OCR 文本），对外是**一个条目**、内部有多个文件 | [JSTOR：Compound objects](https://support.stewardship.jstor.org/hc/en-us/articles/360034046453-Compound-objects-Tiers-2-3)、[OCLC：Compound objects（PDF）](https://help-nl.oclc.org/@api/deki/pages/14759/pdf/Compound%2bobjects.pdf) ⚠️仅看到标题与目录级信息（JSTOR 页面被 Cloudflare 拦了 403），概念名与用法以行业通用义为准 |
| **容器 / Compilation（与复合对象区分）** | 同上 | 规范里特意把"**复合对象**（本来就是一个东西）"与"**容器/汇编**（人为把若干独立东西放在一起，如专辑、选集）"分成两类 | [JSTOR：Related content — compound objects, containers, compilations](https://support.stewardship.jstor.org/hc/en-us/articles/360052874493-Related-content-compound-objects-containers-and-compilations-Tiers-2-3) ⚠️403，未读原文，仅据标题与检索摘要 |
| **库（Library）而不是真实文件夹** | Eagle | 素材存进库自己的结构里，**文件夹是库内的虚拟组织**，与磁盘目录解耦（这样改名/移动/多归属都不会动磁盘） | [Eagle：Why does Eagle use a "library" instead of an actual folder structure](https://de.eagle.cool/support/article/why-does-eagle-use-a-library-instead-of-an-actual-folder-structure-to-store-data) ⚠️官方支持页，未逐字核 |
| **Miller 列（每层一列）** | Finder / NeXTSTEP / Obsidian 的 Column Explorer | 深层目录用横向空间换纵向空间；单纵向树"到两百个文件夹就不行了" | [Column Explorer](https://github.com/n23eos/column_explorer) ✅已读原文（本项目已按此实现文件浏览） |

**一句话结论**：行业里"把多个文件当成一个东西"有两条成熟路线——
**堆叠/复合对象**（本来就是一个单元）与**集合/容器**（人为归到一起，且一个东西可以同时属于多处）。
用户第 6 条要的是**前者**（"我一次添加的综合内容，本来就是一组的"），第 8 条要的是**后者的能力 + 统一的视图**。

## 二、现状（为什么现在会"分开放"）

- 数据模型是**一件素材 = 一个文件**：`asset` 一行对应磁盘上一个对象（内容寻址），`project_asset` 只表达"归属哪个项目"。
  "综合"在【添加素材】里只是"**批量模式**"（一次收多个不同类型的文件，各存各的），所以它们当然是分开的 —— 这正是用户看到的现象。
- 文件浏览（`/api/fs/*`）是**只读的另一条通道**：它列的是磁盘真实目录，**不经过 `asset` 表**。
  于是切到画廊就只剩库内素材，磁盘上那些没入库的文件"消失了"——用户第 8 条问的就是这件事。

## 三、我的方案（待用户判断）

### 3.1 把"位置"和"归属"彻底分开（这是第 8 条的根）

| 维度 | 含义 | 例子 | 现状 |
| --- | --- | --- | --- |
| **位置（位置/来源）** | 文件在磁盘上的真实坐标 | `<内容目录>\<项目素材>\...`、`<库目录>\objects\...` | 已有（`file` 表 + `source_root`） |
| **归属（虚拟组织）** | 人给内容加的分组，可多层、可多归属 | 项目 / 子项目 / 以后可能的标签 | 已有（`project`、`project_asset`） |
| **单元（一件内容）** | 画廊里的一张卡 | 一个 png、一段 mp4、**或者一组综合内容** | 已有（`asset`），缺"一组" |
| **视图范围（scope）** | 画廊当前在展示什么 | 全部 / 某个项目（含子项目）/ **某个磁盘文件夹** / 搜索 | 只有"全部/项目" |

建议：**给画廊加"范围"概念**——除了"全部内容"和项目，再支持"**这个文件夹**"：
选中磁盘上任意目录时，画廊可以显示"这个目录里的东西"，其中
**已入库的显示正常卡片，未入库的显示带「未入库」标记的卡片**，点一下即导入（沿用已有的 `/api/fs/import`）。
这样"图片/视频/声音/音乐/综合/代码/文本/文件"就能**在同一个画廊里一起出现**，而不是两个互不相干的世界。

关键取舍（这点最需要你拍板）：
- **A. 不自动入库**：文件夹只是"视图范围"，磁盘上没入库的文件仍然只是引用；库里不膨胀。
- **B. 自动入库引用**：浏览到的文件自动在库里建一条"引用型素材"（不复制文件，只登记路径），于是画廊天然包含它们。
  B 更接近 Eagle 那种"库就是一切"的体验，但代价是：`node_modules` 之类一旦被浏览就会污染库（除非继续靠忽略规则挡住），且"未入库/已入库"这条界线会消失。

### 3.2 "综合"改成真正的**一组**（第 6 条）

在 `assets` 之上加一层 **bundle（组/堆叠）**：

```
bundle(id, title, note, cover_asset_id, kind='mixed', created_at)
bundle_member(bundle_id, asset_id, sort_key, role)
```

- 【添加素材 → 综合】一次提交的文件**创建为一个 bundle**（而不是 N 个散素材）：画廊里出现**一张卡**（封面 + "5 件 · 3 种类型"角标），点开是成员列表，也可以"展开成独立卡片"；
- 成员仍然是**一等素材**：能被搜索、能被单独挂到别的项目、能单独进专注模式（现在已有的能力全都不浪费）；
- 删 bundle 默认只删"这一组"（成员回到散件），删成员会让 bundle 自动少一件；
- 项目与 bundle 是两个正交维度：bundle 回答"这些本来是一组"，项目回答"这属于哪个工程"。

**为什么不做成"项目"或"标签"**：项目是"归属"，一个东西只该有一个主归属；标签是横切维度；而"我一次加进去的这批东西"是**内容本身的完整性**，所以应该是独立的一层（行业里也正是把 compound object 和 container 分开）。

### 3.3 画廊怎么同时容纳七类 + 文件

- 卡片按"单元"渲染：单文件素材 / bundle 各一张卡；
- 顶部筛选条现状是 `全部类型 114 / 文本 14 / 代码 0 / …`，加范围后变成两段：**范围（全部 · 项目 · 文件夹）** × **类型（七类 + 未入库）**；
- 未入库的卡片用**虚线边 + 「未入库」角标**区分，避免和"已经在库"的混淆；
- 浏览模式（Miller 列）保持不变，作为"按磁盘找东西"的入口；切到画廊时把当前目录带过去当范围。

## 四、分阶段落地建议（如果方案通过）

| 阶段 | 内容 | 风险 |

## 五、需要用户拍板的问题

1. **综合要不要真的变成"一组"**（bundle），还是只要"添加时都挂到同一个项目/同一个标签下"就够？
2. 画廊显示磁盘文件时，**要不要自动登记为引用型素材**（方案 B），还是只当"临时视图"（方案 A）？
3. bundle 的卡片在画廊里**默认显示一张封面卡**（像 Lightroom 堆叠），还是**默认铺开展示每个成员**（像一摞散件但带同组标记）？
4. 一个素材**能不能同时属于多个项目**？（Zotero 的集合是"可以"；本项目现在是"只能一个"。改成多归属会让"归属"这层更像集合，但会牵动现有 UI 与统计口径。）
