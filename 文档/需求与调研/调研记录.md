1. 需求是"给现有文件夹加索引"还是"集中托管库"？两者的失败模式分别是什么？

## 开发决定

### 需求结论

- **必需**：托管库（复制导入、原文件保留）、统一预览与播放、中文可用的搜索、项目-素材关联、库可重建与可搬迁。
- **可选增强**：代码全文检索、智能集合、AI 打标/转写/自然语言搜索、MCP 接入。
- **仍待核实**：是否要打包给别人用（决定要不要做安装器/自动更新）；Python 3.14.4 较新，若做 Python 侧车需先确认依赖兼容性。
- **已核实消除**：视频编码分布（25/25 h264）、库盘剩余空间（D 234.6GB）——原先列为待核实的项已在本次实测中解决。

### 方案选择

| 决定 | 采用 | 为什么不选其他 |
| --- | --- | --- |
| 形态 | **先做本地 Web 应用**（Node + TypeScript 服务端 + 浏览器前端），**M6 再用 Electron 打包**成桌面应用 | 用户 2026-09-27 决定"先 Web 开发，最后再打包"：浏览器里开发调试最快，媒体预览与虚拟滚动这些难点都能先验完。**服务端选 Node 的关键理由是打包成本**——Electron 自带 Node，套壳几乎零改造；若用 Python 服务端，打包要把整个解释器与依赖捆进去。打包阶段选 Electron 而非 Tauri：✅ Tauri 的 WebView2 播不了 MKV/HEVC（除非嵌 GPL 的 libmpv）；.NET 媒体与虚拟化是短板 |
| 库模式 | **托管复制为主 + 大文件引用 + 内容寻址** | 纯索引模式有 Lightroom missing photo 的既有教训；纯托管又怕路径耦合，故用哈希寻址解耦 |
| 数据层 | **SQLite（better-sqlite3，≥3.51.3，WAL）+ sidecar 双写** | 不引入 Postgres/Docker（单人无必要）；不把元数据只放 DB（Eagle/Billfish 的教训） |
| 搜索 | **FTS5 + 应用层 bigram + ripgrep 做代码** | 不引 Meilisearch/Typesense 常驻服务；不用 trigram（<3 字符坑） |
| 缩略图/媒体 | **sharp + ffmpeg（复用你已有的 full build）** | 不在 UI 线程实时解码大文件；原图不入库 |
| AI | **单一适配器 + 小米 MiMo 云 API，后置异步** | 本地推理路线被 DirectML 降级与 opset 限制拖累；你的 key 与调用经验已就绪 |
| 智能集合 | **存 JSON 查询 AST** | 存 SQL 字符串会在 schema 演进后全部失效 |

## 补充调研（2026-09-27 晚）：专注模式、编辑能力、文件浏览模式

用户提的三项改造（所有类型都要专注模式 / 文本代码要能编辑 / 图标化与面板可关闭 / 目录怎么专业展示）里，有三处需要外部证据才敢定方案。

| 问题 | 证据 | 状态 |
| --- | --- | --- |
| 长音频能不能在浏览器里画真实波形？ | [wavesurfer.js 性能文档](https://wavesurfer.xyz/docs/performance/)明确写：用 Web Audio `decodeAudioData` 会把整个文件解成裸 PCM，**60 分钟立体声轻易超过 500MB**；官方给的两条出路是①改用 `<audio>` 元素做后端（浏览器流式播放，内存不随长度涨）②**预先算好 peaks 数据**。同站 [pre-decoded peaks 文档](https://wavesurfer.xyz/docs/peaks/)给了生成方式（BBC [audiowaveform](https://github.com/bbc/audiowaveform) `--pixels-per-second 20 --bits 8`）并指出**每声道 1000–2000 个点就够**，点越少内存与 CPU 越省。 | ✅已验证（官方文档原文） |
| 编辑器选哪个？ | [Monaco vs CodeMirror 6 对比（PkgPulse，第三方指南）](https://www.pkgpulse.com/guides/monaco-editor-vs-codemirror-6-vs-sandpack-in-browser-2026)：Monaco **就是 VS Code 的编辑器内核**，完整 IntelliSense，但打包 **2–5MB gzip**、需要 web worker、SSR 要动态加载；CodeMirror 6 模块化 **约 50–200kB**，语法高亮/行号/折叠/搜索/多光标齐全，只是没有类型智能，移动端更好。 | ⚠️仅宣称（第三方对比文，未在本机实测体积） |
| 深层目录怎么展示才"专业"？ | [Column Explorer（Obsidian 的 Finder 式 Miller 列插件）](https://github.com/n23eos/column_explorer)把理由讲得最清楚：单个纵向树"到两百个文件夹就不行了——展开一个分支把其他都挤出屏幕，折叠起来就丢失位置，还要在一列宽里滚动找已知文件名"；Miller 列**用横向空间换纵向空间，每层一个列，同时看到在哪、从哪来、下一步是什么**，这正是 Finder 列视图与 NeXTSTEP 用了三十年的做法。它的配套做法也值得抄：面包屑跳转、每列可拖宽、`Space` 快速预览、每文件夹独立的排序与列表/图标切换、多选与拖拽、按类型筛选、排除规则。 | ✅已验证（项目 README 逐条写明） |

**由此定下的方案**（用户已确认，见 [设计-专注模式与文件浏览](../设计/设计-专注模式与文件浏览.md)）：

1. 音频波形**服务端用 ffmpeg 解 PCM 算 peaks**（本机已有 ffmpeg，不引入 audiowaveform 这个额外二进制），按内容哈希缓存在 `derived/peaks/<hash>.json`，前端用 `<audio>` 播放 + canvas 画 peaks——完全避开"整段 PCM 常驻内存"那条坑，也**不画假波形**。
2. 文本/代码的专注模式用 **CodeMirror 6**（模块化、无 worker、行号/语法高亮/搜索/折叠/多光标齐全，约 50–200kB），并明确**保存 = 生成新版本（新哈希对象）**，另给"写回原文件"按钮（默认关闭 + 二次确认），避免破坏"原文件绝不动"的承诺。**不选 Monaco 的理由**：它确实是 VS Code 内核、有 IntelliSense，但要 2–5MB + web worker 配置，而这里只需要"能好好编辑文本与代码"；真需要类型提示时再换（编辑器层会包成一个组件，换实现不影响别处）。
3. 文件浏览模式采用 **Miller 列 + 详情表（名称/修改日期/类型/大小）+ 右侧预览**，即用户截图那种信息密度，但补上面包屑、排序、多选、预览与"导入到库/移入回收站/在资源管理器中显示"这些管理动作。
