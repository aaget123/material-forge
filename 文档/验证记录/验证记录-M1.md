## 结论

**成功次数/实际运行次数**：上表 1–12 共 12 项通过，其中 **#6、#7 是先发现失败、修复后复验通过**，不计入一次通过；#9–#11 是真删/真移文件的高风险项，均在真实数据上执行并核对了原文件完整性。

**耗时与成本（有测量）**：

| 项 | 数值 |
| --- | --- |
| 复制导入 113 文件 / 293 MB | 0.5 s（同盘复制） |
| 全量重扫（含 99 次探测 + 99 张缩略图） | 25.5 s |
| 增量重扫（无变化） | 0.18 s |
| 库内占用 | objects 293.0 MB + sidecar 113 个 + 缩略图 99 张（1.8 MB）+ index.db 228 KB |
| 外部 API 费用 | 0（AI 层未开始） |

**M1 期间发现并修复的缺陷（全部已在本次复验）**：

| # | 缺陷 | 暴露方式 | 修订 |
| --- | --- | --- | --- |
| F1 | `relink` 崩溃 `UNIQUE constraint failed: source_root.path` | 真改名库目录后执行 relink | 新增 `canonicalizeManagedRoot`：挑规范托管根 → 合并其余根的文件行 → 删除多余根行 |
| F2 | 检索结果重复：一个素材有 2 个文件行 → 「<剧集>」5 条变 10 条 | 导入后检索 | 新增 `PREFERRED_FILE_JOIN`：每个素材只取一个代表文件行（优先托管对象） |
| F3 | 统计翻倍：大小 293 MB→586 MB、缩略图 99→198 | 导入后看统计 | 字节数/缩略图数改为按 `asset` 统计，不再 JOIN `file` 后 SUM |
| F4 | 缩略图按 `asset.id` 命名，删库重建后 id 变化 → 整批失效 | 重建演练前的设计走查 | 改为**按内容哈希命名**（`derived/thumbs/<hash>.webp`），服务端缓存缺失时就地补生成 |
| F5 | 重建后 FTS 只索引哈希路径 → 「<剧集>」**0 条** | 删库重建后检索 | 新增 `asset.display_path`（来源相对路径），展示与 FTS 都用它；sidecar 的 `source` 字段成为重建依据 |
| F6 | `scan` 不做哈希去重，重建后再扫描出现 113 个重复素材 | 删库重建后重扫 | 扫描按 hash 复用/改挂素材，清理空壳素材，扫描末尾兜底 `mergeDuplicateAssets` |

**查证过但不是缺陷的**：曾怀疑 sidecar 里 `source.rootPath` 的中文路径乱码（显示为 `鍐呭`）。用字节级读取核对码点为 `U+5185 U+5BB9`，**数据完全正确**，那是 PowerShell 读取时的显示假象。没有据此改动任何代码。

**未验证部分及影响**：

- 音频/音乐/PDF 只做了类型分支静态检查；这三类素材的导入、预览、回收**没有证据**。
- 「用系统默认程序打开」的成功分支仍未触发。
- `missing`（文件被外部删除）在 M1 下没有制造过真实场景；软删除路径已验，硬缺失未验。
- 搬家只测了**同盘改名**；跨盘、换机器、库放在移动硬盘的场景未测（`relink` 依赖 `LIBRARY_DIR` 与相对路径，理论上成立，但未实测）。
- 备份只生成了校验和清单（`manifests/checksums-*.txt`），**没有做过一次真实恢复演练**——按 M0 结论，这仍属未验证。
- 万级素材的性能与 FTS 退化（M4）、AI 层（M5）、Electron 打包（M6）均未开始。

**已知限制（继承 M0）**：SQLite 3.51.2 低于 WAL-reset 修复版 3.51.3；当前单进程单写者不触发，**引入多进程写入前必须先升级**。库目录不得放在 OneDrive/坚果云/网络盘。

**界面待打磨项（不属缺陷）**：
1. 切到「回收站」时，网格会短暂显示上一次的库内列表，直到数据返回；建议 M2 加一个加载态。
2. 「用系统默认程序打开」打开的是**库内托管对象**（内容寻址，文件名是哈希），所以外部程序的标题栏会显示 `24b653e2….png` 这种名字。行为上是对的（库是真相），但不好认；可考虑在"有原始文件"时补一个「打开原文件」按钮。

**下一步建议**：M2（统一预览器：音频波形、PDF/Office、代码高亮、视频悬停预览）之前，先补两件小事——① 用一次真实的「用系统默认程序打开」把 #14 关掉；② 在小样本上做一次 `VACUUM INTO` 备份 + 恢复演练，把"可恢复"从设计走查变成实际执行。

## 追加验证（用户反馈驱动，2026-09-27 当天）

用户反馈：「系统默认程序打开没用」，附截图 `出错: 401 {"error":"缺少或错误的 x-pm-token"}`。查下来是**两个独立问题**，都已修复并复验。

### 问题一：401 —— 服务重启后 token 变了，久置的标签页仍持旧 token

- **复现**：用旧 token 调 `POST /api/open/15` → 401，错误文本与截图完全一致（服务端确实收到请求，只是凭据过期）。
- **成因**：服务每次启动生成随机 token（安全设计），而我在 M1 期间多次重启服务；用户浏览器里那个标签页是更早一次会话加载的。
- **修订**：前端在任何请求收到 401 时，**自动刷新一次页面**从 HTML 里取回当前 token（用 `sessionStorage` 标记防止刷新循环）；刷新后仍失败才提示用户重新打开页面。
- **复验（真实重启服务做实验）**：页面持 token C（`8a925ff85f`）→ 杀掉服务重启为 token D（`e93efd9766`）→ 在页面点一次素材触发请求 → `documentGeneration` 由 2 变 3（**页面确实自动刷新了**）→ 刷新后页面 token 前缀 `e93efd9766` **与服务器当前 token 一致**、错误提示为 `null`、113 素材与侧栏计数正常、点开素材能正常渲染详情。

### 问题二：即便 token 正确，「用系统默认程序打开」也打不开任何程序（真缺陷）

- **复现**：用**正确** token 调 `POST /api/open/15` → HTTP 200 `{"ok":true}`，但进程核对显示**没有任何新进程**。接口说谎了。
- **成因**：原实现是 `spawn('cmd.exe', ['/c','start','',路径])`。Node 在 Windows 上**不会为空字符串参数生成引号**，空标题消失后 `start` 把**路径当成窗口标题**，于是既没打开文件，也没什么可见反应。
- **修订**：改用 `explorer.exe <路径>`（按系统关联启动默认程序，正确处理 Unicode 路径，也不需要标题占位参数），并保留一个 `cmd /c start pm-open <路径>`（**非空**标题）作为兜底。
- **复验（进程级证据）**：

| 素材类型 | 默认程序 | 证据 |
| --- | --- | --- |
| 笔记 `.md`（#15） | ima.copilot | 调用后新增进程 `explorer` + `ima.copilot` |
| 图片 `.png`（#14） | BaiduNetdiskImageViewer | 调用后新增进程 `BaiduNetdiskImageViewer` + `dllhost` + `explorer` |

> 验证时确实在你桌面打开了这两个程序窗口，属于本次验证的副作用。

### 问题三：回收站里看不到缩略图 / 图片不显示

- **反馈**：删除恢复本身可用，但"在回收站里不显示，图片是不显示的"。
- **成因**：`getAsset()` 默认过滤 `deleted_at IS NULL`，于是 `/thumb/:id`、`/media/:id`、`/api/text/:id` 对已删除素材一律 404；前端因此在回收站视图里**故意**只渲染扩展名占位、把预览换成文字提示。结果是回收站里看不出删了什么，只能盲恢复——功能上等于不可用。
- **修订**：
  1. `getAsset(db, id, { includeTrashed })`：新增允许取 `status='trashed'` 文件行的 JOIN（托管对象此时位于 `trash\`）；
  2. `/thumb/:id`、`/media/:id`、`/api/text/:id` 与详情接口的 `?trashed=1` 都放开对回收站素材的支持——缩略图缓存本来就是**内容寻址**的，删素材不会删缓存，恢复后还能直接复用；
  3. 界面：回收站网格照常渲染缩略图；详情面板改成"提示条 + 正常预览"，不再用文字顶替图片；
  4. 顺手修掉一句错话：回收站素材的「库内」一栏原本显示"仅引用（未导入）"（因为 `inLibrary` 只统计 `status='present'` 的托管行），现在显示"托管副本在回收站"。
- **复验（接口层）**：`/thumb/14` → 200 `image/webp` 17 262 字节；`/media/14`（Range）→ **206** / 1024 字节；`/api/text/15` → 200 / 12 548 字节；`/api/trash` 列表中图片项 `thumbAt=true`。
- **复验（浏览器，DOM 证据）**：回收站网格 `cards=1 / thumbImgs=1 / thumbsLoaded=1`，缩略图实测 **480×240**；详情预览 `<img>` `complete=true`、**2752×1376**；提示条文案正确；点"从回收站恢复"后侧栏回到 113、`293.0 MB`；后台核对 113 素材 / 回收站 0。
- **证据方式说明**：Tabbit 的截图捕获在本机连续失败（`SCREENSHOT_CAPTURE_FAILED`），因此这一项改用 DOM 尺寸证据（`complete` + `naturalWidth/naturalHeight`）。对"图片是否真的显示出来"这个问题，DOM 尺寸比截图更硬。
- **注意**：笔记/文档本来就没有缩略图（只有图片与视频抽帧），回收站里它们显示为扩展名占位（如 `MD`），这是设计如此，不是同一个问题。

### 功能追加：看图模式（图片专用全屏浮层）

**反馈**：详情面板里的图片只有 320px 高、不能缩放，"放大功能不太好用"，希望有专门看图模式。

**实现**（手写，不引第三方库）：全屏浮层 + 自由缩放
- 滚轮以**光标位置**为中心缩放（`tx/ty` 随焦点重算，而不是以画面中心缩放）
- 拖拽平移（`setPointerCapture`）、双击在「适应窗口 / 100%」间切换
- 顶栏：上一张/下一张、缩放百分比、适应窗口、100%、旋转 90°、外部打开、关闭
- 快捷键：`Esc` / `←→` / `+−` / `0` / `1` / `R`；窗口尺寸变化时若仍在「适应窗口」状态会自动重算
- 只在图片上生效；网格里双击打开，详情面板也有入口

**复验（真实浏览器操作，DOM 数值证据）**：

| 操作 | 预期 | 实测 |
| --- | --- | --- |
| 双击图片 | 浮层打开并解码原图 | `.viewer` 可见，`naturalWidth×Height = 2752×1376`，自动适应到 `scale=0.507994`（51%） |
| 滚轮放大（光标在画面左偏 35%/40%） | 以光标为中心放大，`tx/ty` 必须非 0 | `scale 0.508 → 0.796`（精确等于 `1.0015³⁰⁰` 倍），且 `tx=129.455, ty=40.0855` —— **中心缩放会让 tx/ty 恒为 0，这里非 0 即证明是光标锚定** |
| 滚轮缩小 | 变小 | `scale=0.324021` |
| 拖拽 (+120, +60) | 平移量与手势一致 | `tx=120, ty=60` |
| 适应窗口 / 100% / 键 `0` / 键 `1` | 0.508 / 1 / 0.508 / 1 | 完全一致，百分比标签同步为 51% / 100% |
| 键 `→` 翻页 | 计数器与图片都变 | `1 / 71 → 2 / 71`，`img.src` 改变，标题 <角色A> → <角色B> |
| 键 `R` 旋转 | 出现 rotate | `transform: translate(0px, 0px) scale(0.507994) rotate(90deg)` |
| 键 `Esc` | 浮层关闭 | `.viewer` 数量 0 |
| 双击视频卡片 | 不应打开看图模式 | `.viewer` 数量 0（只选中） |

**证据**：（截图仅本地保留，不入仓库） 实际像素显示，画面被视口裁切——这正是"真的放大到原始像素"的表现）。

**未验证**：触摸屏双指缩放、超大图（>50MP）的流畅度、连续翻页时的内存占用。

### 这次暴露的方法论教训

1. **接口返回成功 ≠ 功能生效**：`{"ok":true}` 只证明代码走到了 return，不证明外部程序被打开。外部动作必须核对**外部状态**（这里是进程列表），这正是指南里"文件生成、外部写入要检查实际状态"的意思。
2. **改动后必须重建前端**：第一次复验失败，是因为我改了 `web/src/api.ts` 却没跑 `web:build`，浏览器仍在跑旧 bundle（`documentGeneration` 没变就是线索）。看构建产物而不是看源码，才发现这一点。
3. **token 过期这类"环境状态"要在客户端自愈**，不该把 401 直接甩给用户——用户没有任何办法从那个报错里恢复。
4. **软删除最容易漏的不是数据，而是依赖该状态的附属能力**（缩略图、预览、文本读取）。加一个"过滤已删除"的条件时，要顺着**所有读取路径**查一遍，而不是只管列表接口。
