### ⛔ 失败过的两次（都记下来，避免下次再踩）

**1. 第一版图标把形状画在了外层盒子上。**
`Icon` 用 inline style 给外层 `.pmi` 设 `width/height`，而 CSS 里又给同一个元素设 `width: 56%`——inline 优先，于是"桶身"实际是 56px 见方，桶盖相对桶身定位后直接撑出盒子（放大到 64px 看图标一览时一眼可见）。
**改法**：固定成两层结构 `.pmi`（只吃尺寸）→ `.pmi-b`（`inset: 0` 铺满）→ `::before/::after`，所有几何坐标一律是"外层盒子的百分比"，任何 size 都不变形。同时把 `reveal`（"在资源管理器中显示"）这个画不好的图标先摘掉，等文件浏览模式真要用时再好好设计。

**2. 用 PowerShell 改 CSS 把文件写坏了（这一条代价最大）。**
`Get-Content` + `Set-Content -Encoding UTF8` 往返把中文注释按 GBK 解码再按 UTF-8 重写，注释变成乱码；更糟的是某个注释末尾的 `。*` 被吞成 `銆?`，**`*/` 的星号没了**，于是那条注释一直吞到一百多行之后的另一个 `*/`——`.main`、`.main-inner` 等布局规则整段被当成注释丢掉。
症状很有欺骗性：图标全都正常渲染（在注释之前），但主区宽度塌成内容宽度（`flex-grow` 实测 `0`），右侧出现大片空白。
**改法**：`git checkout -- web/src/styles.css` 回到已提交版本，再用编辑工具（不经过 PowerShell 编码往返）重新应用这一轮的 CSS 增量；修复后构建产物里 `.main{` 回来了，`flex-grow` 恢复到 `1`，上表数据即修复后的实测值。
**教训**：改非 ASCII 源码不要用 PowerShell 的文本读写往返，一律用能保证 UTF-8 的编辑工具；改完要检查构建产物里关键规则是否还在。

## 第二步：音频真实波形 + 声音/音乐的专注模式（2026-09-27，已完成）

### 做了什么

| 层 | 实现 |
| --- | --- |
| 后端 | `core/peaks.ts`：ffmpeg 把音频解成 **8kHz 单声道 s16le 从 stdout 流式读出**，边读边按桶取峰值，归一化到 -1..1；内存只与桶数有关、与音频长度无关。桶数固定 1600（wavesurfer 文档给的经验值：每声道 1000–2000 点足够）。缓存写 `derived/peaks/<内容哈希>.json` |
| 接口 | `GET /api/peaks/:id`：命中缓存直接返回，缺失时现算并写缓存；**同一个哈希的并发请求共用一个 promise**（不重复跑 ffmpeg）；非音频扩展名返回 415；回收站里的素材也能取 |
| 前端 | `WaveformPlayer.tsx`：canvas 画对称峰值包络（已播放部分用主色）、点击/拖动跳转、播放/暂停、进度条、0.5–2× 倍速、音量、空格/←→/↑↓/0 快捷键。播放交给 `<audio preload="metadata">` 流式处理，**不把整段 PCM 解码进浏览器** |
| 外壳 | `FocusOverlay.tsx`：所有模态共用的专注模式外壳（标题/路径/翻页/计数/外部打开/关闭 + 底部快捷键提示，`Esc` 关闭、`[` `]` 翻页）。图片沿用已有的看图器（它本身就是完整专注形态），声音/音乐接波形播放器；视频、文本/代码、综合的主体留到下一步 |
| 入口 | 详情栏动作区新增 `进入专注模式` 图标（主操作）；图片/声音/音乐双击卡片或单击预览图也能进 |

## 第三步：视频 / 文本代码 / 综合的专注模式 + 去掉面板上的"用系统默认程序打开"（2026-09-27，已完成）

### 做了什么

| 模态 | 主体 | 关键点 |
| --- | --- | --- |
| 视频 | `VideoStage.tsx` | "放大看视频"= 对 `<video>` 做 `transform`（缩放 + 平移），**不重新编码**；滚轮以光标为中心缩放、拖拽平移、双击切换适应/100%、逐帧 `,` `.`、倍速 0.25–2×、静音、音量、`+−`/`0`/`1`/`M` 快捷键 |
| 文本 / 代码 | `TextFocus.tsx` | CodeMirror 6：行号、语法高亮（11 种语言按后缀挑）、括号匹配、搜索替换、折叠、多光标；`Ctrl+S` 保存；`放弃修改` 回滚到上次保存；未保存标记 + 行/字符/版本计数 |
| 综合 / 其他 | `MixedFocus.tsx` | 文件检视：元数据 + **首部字节 hex**（用 Range 只取 4KB，几 GB 的文件也不读进来）+ **魔数识别**（ZIP/PDF/PNG/RAR/7z/PSD…）+ **文本嗅探**（像文本就直接显示原文）；PDF 直接整窗内嵌阅读器 |
| 面板 | `Inspector.tsx` | 按用户要求**去掉**"用系统默认程序打开"按钮；它只留在专注模式工具栏里，作为无法页面内预览类型的兜底 |

**编辑保存语义**（用户确认的方案，`core/organize.ts` 的 `saveTextVersion`）：

- 默认**存成新版本**：新内容 → 临时文件 → sha256 → 新对象（内容寻址，天然去重）→ 当前托管文件行指向它 → 旧内容记进 `asset_version` 表；
  **绝不原地改写托管对象**，因为"对象路径 = 内容哈希"的契约一旦破坏，去重与 relink 都会失效；
- **「写回原文件」**是可选动作，需二次确认；执行顺序是**先落库内新版本、再写原文件**，即使写原文件失败，库里也已经有新版本；
- 新增 `asset_version` 表 + `GET /api/assets/:id/versions`；`verifyLibrary` 把这些历史版本哈希也算作"已索引"，所以保存编辑不会让 `verify` 冒出"库外对象"。

## 第四步：文件浏览模式（Miller 列 + 详情表 + 预览）（2026-09-27，已完成）

### 为什么做成这样

调研里 [Column Explorer](https://github.com/n23eos/column_explorer) 把单纵向树的问题讲得最清楚："到两百个文件夹就不行了——展开一个分支把其他都挤出屏幕，折叠起来就丢失位置，还要在一列宽里滚动找已知文件名"。所以导航用 **Miller 列**（每层一列，同时看到"在哪、从哪来、下一步"），信息密度用**详情表**（名称/修改日期/类型/大小，可排序）——正好是用户截图里那四列，但补上了面包屑、排序、动作与预览。

### 做了什么

| 层 | 实现 |
| --- | --- |
| 后端 | `core/fsbrowse.ts`：`listDirectory()` 按层列举**任意本地目录**（目录在前、中文按本地序、单层上限 5000 项、单项读不动就跳过而不是整层失败）；用分批 `IN` 查询把这些路径在索引里的状态一次带回来（`assetId` / 是否在回收站）；`listRoots()` 给出配置的根目录 + 盘符 |
| 接口 | `GET /api/fs/list?path=`、`GET /api/fs/roots`、`POST /api/fs/import`（把磁盘上的某个文件复制进库，**原文件不动**）、`POST /api/fs/reveal`（在资源管理器中定位） |
| 前端 | `BrowseView.tsx`：Miller 列（点目录即开下一列，不用"先选中再双击"）、面包屑跳转、"跳到…"根目录选择器、每层计数与忽略数、`列表 / 详情` 两种密度、详情模式表头点击排序、选中项动作条（导入到库 / 在资源管理器中显示 / 复制完整路径 / 移入回收站 / 在右侧详情里打开）、上次浏览路径记在 `localStorage` |
| 边界 | "浏览 ≠ 索引"：被忽略规则挡住的目录**照样能点进去看**，只是挂着「忽略」标记；这一层**不重命名、不删除磁盘文件**——那是资源管理器的活，本工具只在用户点「导入到库」时复制一份 |

## 第七步：架构改造第一半 —— 组（bundle，综合=一组）

### 做了什么

| 层 | 实现 |
| --- | --- |
| 数据 | 新增 `bundle`（标题/备注/封面/创建时间）+ `bundle_member`（成员，含排序）两张表。**素材本身一行没改**：成员仍是一等素材，能搜索、能挂项目、能进专注模式 |

| 接口 | `GET/POST /api/bundles`、`GET /api/bundles/:id`（含成员）、`POST /api/bundles/:id/expand`（拆组，成员留下当散件）、`POST /api/bundles/:id/members`、`DELETE /api/bundles/:id/members/:assetId` |
| 前端 | 画廊默认**一组只显示一张代表卡**（封面优先，封面被筛掉时用第一个成员），卡片左上角角标「一组 N 件」，点一下展开/收起；「添加素材 → 综合」一次加进来 2 件以上时**自动组成一组**（标题取用户填的标题，没填就是「综合内容 · 日期」）；建组失败单独提示，不影响"素材已入库"这件事 |
| 收尾 | 清空回收站后 `pruneBundles()` 把只剩 0/1 个成员的组自动解散（一个成员的"组"是空壳）；组成员被摘空、封面被摘走时都会自动修正 |

## 第十一步：同一张卡出现两次（重复且同步）—— 根因与修复

用户描述的现象："同一张卡出现了两次，而且还是同步，同步被修改"。两张卡是同一份数据，说明**同一件素材在列表里被返回了两行**（不是真的多了一条记录，所以查数据库看不到重复）。

### 根因

列表查询里挂着两个 `LEFT JOIN`：

- `LEFT JOIN project_asset pa ON pa.asset_id = a.id`（归属表是**多对多**）
- `LEFT JOIN bundle_member bm ON bm.asset_id = a.id`（组的成员表）

只要某件素材**同时挂了两个项目**（或同时属于两个组），JOIN 就会把它变成两行 → 画廊渲染出两张一模一样的卡；两张卡读的是同一条数据，所以"改一张另一张跟着变"。同理 `SELECT COUNT(*)` 也会把它数成两件（计数虚高）。

### 修复（两层）

| 层 | 改动 |
| --- | --- |
| 查询层 | 三条列表查询（默认、FTS 搜索、子串搜索）全部加 `GROUP BY a.id`；三条计数查询改成 `COUNT(DISTINCT a.id)`。这样任何 JOIN 出现多值都不会再重复行/重复计数 |
| 渲染层 | `visible` 计算里再加一道按 id 去重（`seenIds`），保证任何列表来源（含"文件夹范围"的映射）都不会把同一件塞两次 |

### 实测（临时库）

1. 建两个项目"项目甲/项目乙"，加一件素材挂到甲；
2. 人为往 `project_asset` 再插一条到乙 → 该素材**归属行数 = 2**（复现条件成立）；
3. 调 `GET /api/assets` → **total=1、返回 1 条、重复 id 数 0**，项目显示为"项目甲"。

修复前这条查询会返回 2 行、total=2。真实库当前没有多归属素材（0 条），但这个类别的隐患已经堵住。

## 第十三步：画廊遮挡（第二次反馈）—— 详情栏打开时列数没重算

用户第二次反馈："选中会展示全部，选中的一部分被遮挡了"。看截图能确认：窗口 1900 宽、右侧详情栏打开、主区约 1242，但卡片仍是 **280px × 5 列**（5×280+6×16 = 1496）→ 第 4 列被详情栏压住。

### 根因

网格的列数是按"测到的容器宽度"算的，而**详情栏开合是有过渡动画的**：动画期间宽度在变，最后一拍如果没被重新测到，列数就停留在旧宽度上（面板关着时的 5 列）。上一轮我加的"每次渲染自校正"没能覆盖动画收尾那一拍。

### 修法

- `VirtualGrid` 新增 `revision` 参数：面板开合、选中变化、文件夹范围变化时数值变化；
- `revision` 一变，在 **0 / 120 / 320 / 620ms** 各补测一次宽度，确保过渡结束后用的是**最终**宽度；
- 同时给窗口 `resize` 也挂了测量。

### 实测（1900×968，与你截图同一场景）

| 状态 | 容器宽 | 卡片宽 | 列数 | 横向溢出 | 最右卡片超出容器 |
| --- | --- | --- | --- | --- | --- |
| 详情栏关着 | 1201 | 280 | 4 | 0 | -39px（内收，未裁切） |
| **点卡片 → 详情栏打开** | 1185 | **276（已重算）** | 4 | 0 | -39px |
| 再等 1.2 秒（动画结束） | 1185 | 276 | 4 | 0 | -39px |

修复前这里是"5 列 × 280px"排在 1242 宽的容器里，右边一列必然被压住。
