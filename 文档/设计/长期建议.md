# 长期建议（不是必要约束）

本项目的判断准则里，标**默认建议**的 5 条放在这里。它们不进 [协作规则](../../协作规则.md)，因为并非每次改动都必须执行；但违反的代价是**返工**，不是数据损失——所以默认照办，有项目证据或用户明确要求时可以调整，调整时简记理由。

`[待验证]` 的含义：尚无本项目证据支持，等真出现反例或正例再升降级。

## 一、功能之间低耦合、高内聚（`[方法建议]`）

一个文件的事别拆到三个地方（高内聚）；改 A 不需要动 B（低耦合）。已有实践：`core` 不依赖 UI 与 HTTP、系统动作只由服务端执行、视图状态归界面而数据归核心。

这条不只是代码质量偏好：**耦合一高，任何升级都会变成重写**，协作规则里"升级 > 组合 > 新建"和"同类型先立标准"就都保不住了；耦合低的改动才能被小块验证。

实例：因为 `core` 被约束成不依赖 UI 与 HTTP，索引正确性可以先用 CLI 在真实素材上验，不必等界面做完。反例是文件浏览模式那套 `fs/list` 接口——它与素材库主线耦合太深，最后**整套移除**（连同 `BrowseView` 组件一起删），而不是继续维护。

## 二、同一类型内容先立"简单标准"，再往里加（`[待验证]`）

同类东西（页面、图标、叠加层、接口、派生缓存…）**先定一个最小范式，之后照抄**，让修改与新增有唯一参照。标准要简单到能一眼看完：**一个示例文件 + 几条必须遵守的形状**，不写成规范手册。

新增时照哪个文件抄：

| 类型 | 照抄的参照 | 必须遵守的形状 |
| --- | --- | --- |
| 页面骨架 / 视图状态 | `项目管理器/web/src/App.tsx` | `侧栏（可关）｜主区网格或列表｜右侧详情栏（选中即出现）` |
| 图标按钮 | `web/src/components/Icon.tsx` | 纯 CSS 画，24×24、1.6px、`currentColor`，带 `title` + `aria-label` |
| 专注模式 / 叠加层 | `web/src/components/FocusOverlay.tsx` | 共用外壳，按模态换主体（现有：图/视频/音频/文本/综合） |
| 列表与卡片 | `web/src/components/ContentCard.tsx`、`ContentList.tsx` | 卡片与列表两种排布共用同一份数据形状 |
| 接口 | `项目管理器/server/server.ts`（路由表见 `server/openapi.ts`） | `GET /api/<资源>/<id>`，动作走明确子路径 |
| 派生缓存 | `core/`（缩略图、`peaks.ts`、`derived/<类型>/<hash>.<ext>`） | 按内容哈希命名，可重建、不进备份 |

立标准的时机：做**第一个**同类内容时就定下来并写进本表；发现第二处写法不一致时马上统一，不要等第三处。
理由：有唯一参照，改动才可预测，也让 AI 能在不反复确认的情况下正确新增。
这条标 `[待验证]` 的原因：本项目**尚无"因为没标准而返工"的记录**；真出现第二次写法不一致时才升级。

## 三、方案先定骨架与不可逆项，细节留给证据（`[方法建议]`）

样品前只定"错了要重做数据或契约"的那些（真相来源、技术栈与形态、外部边界）；目录划分、性能优化、抽象提取等，等真实需求暴露再定。凡是"先做 A 能让 B 更便宜"的，优先 A。

实例：「先 Web 后打包」——服务端用 Node，M6 用 Electron 套壳几乎零改造，所以打包放最后**反而更便宜**；代价是从 M0 起就要守住那 6 条打包约束（见 [开发建议](开发建议.md) §13.2）。

## 四、记录决定，并写下当时的理由和反例（`[已验证]`）

重要取舍记在本目录（`文档/设计/`），写清"选了什么、为什么、什么条件下会推翻"。**"不做"的清单与"做"的一样重要**，显式写下来，否则范围会悄悄膨胀。

实例：选 Electron 不选 Tauri 的理由写清了（WebView2 播不了 MKV/HEVC）；"不做"清单同样显式（不做本地推理／转码工厂／多用户／云同步／插件系统）。本轮核对时正是靠它，没有把 MCP 接入与 Electron 打包当成该做的工作。

## 五、依赖与环境只在本项目里（`[待验证]`）

**装依赖、配环境、放工具，都限制在项目自己的目录内**，不往机器全局写。

| 要做的事 | 这么做 | 不要 |
| --- | --- | --- |
| 装依赖 | Node 用项目内 `node_modules`（`npm i` 默认）；Python 用项目内虚拟环境（`.venv/`） | `npm i -g`、全局 `pip install`（除非确有跨项目需要的工具） |
| 放可执行工具 | 随项目目录（或指路径） | 改全局 `PATH`、装全局服务、改注册表 |
| 配环境变量 | 写在项目内的启动脚本或 `.env`（且 `.env` 进 `.gitignore`） | 改用户级/系统级环境变量 |
| 记环境要求 | 版本写进 `README` 或 `package.json` 的 `engines` | 依赖"我这台机器上正好装了" |
| 用机器绝对路径 | 可以，但集中放一处并在文档里注明 | 散落在源码多处、把绝对路径当唯一事实 |

理由：**项目内聚，才搬得走**。依赖与环境散在机器各处会同时踩三个坑——换机器或重装后跑不起来；两个项目的工具链版本互相污染（A 项目升了全局包把 B 项目搞坏）；`git clean`、删目录、搬家都无法真正清理干净。

边界（不必教条）：机器上本来就要有的东西——git、Node 运行时、系统自带程序——不算项目依赖。本项目的 `core/config.ts` 里确实写死了 `<内容目录>\shipingchuli\...ffmpeg` 这类机器路径，那是**有意选择**（复用已有 ffmpeg，不重新下载），做法上是集中在一处配置里、并写进文档；新增这类机器相关配置时沿用同一做法。
